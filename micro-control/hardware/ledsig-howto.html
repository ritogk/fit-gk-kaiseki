純正LEDロービームの信号を記録する手順

フィットGK5前期。車側カプラーの信号ピンYに何が流れているかを、ESP32で記録してMacで判定する。ファームは firmware/led_sig_rec、解析は tools/ledsig.py。

0全体像

車の配線から信号だけを抜き出し、保護回路で3.3V以下に下げてESP32に入れる。ESP32はHighとLowの時間をµs単位で測ってMacへ送り、Macのスクリプトが「一定・PWM・通信」のどれかを判定する。ユニットは車につないだまま、いつも通り点灯させた状態で測るのがポイントである。

1保護回路(分圧+ツェナー)

ESP32の入力は3.3Vまでしか耐えないので、抵抗2本で電圧を2/3に下げ、ツェナーダイオードで上限を3.3Vに抑える。抵抗は「信号側に10kΩ、GND側に20kΩ」の向きにする。逆にすると5Vの信号が1.67Vにしかならず、ESP32がHighと判定する約2.5Vに届かないため、何も記録されない。

入力電圧ごとに、ESP32に届く電圧は次のようになる。どの場合もHighとLowが正しく分かれ、3.3Vを超えない。

車側の信号分圧後(計算)ツェナー後ESP32の判定
0V0V0VLow
5V3.33V約3.0〜3.3VHigh(2.5V以上)
12V8V3.3V前後に制限High
14.5V(エンジン始動中)9.7V3.3V前後に制限High

テスターで「0↔5V」と出たのは、12VのPWMをテスターが平均した値の可能性もある(推測)。そのため、12Vが来ても壊れない回路にしてある。

2ブレッドボードでの組み方

部品は抵抗2本とツェナー1本だけなので、ブレッドボードで組める。車からの線は3本(信号Y、GND、予備で信号X)で、ESP32へはGPIO10とGNDの2本を渡す。パワー線ではなく信号線なので、ブレッドボードで問題ない。

車のGNDとESP32のGNDを必ずつなぐ。つながないと基準の電圧がずれ、信号が読めないうえ、意図しない経路に電流が流れることがある。

3ユニットをつないだまま信号を取る

カプラーを抜いて車側だけを測ると、信号が出ないことがある。車側がスイッチの役(オープンコレクタ)で、電圧はユニット側が供給する方式なら、ユニットを外した時点で信号が消えるためである(推測)。そこで、カプラーはつないだまま、電線が入っている後ろ側から細いピンを差し込んで端子に当てる。この方法をバックプローブという。

ピンはバックプローブ用の細いピン(エーモン等で数百円)か、太めの縫い針を使う。防水ゴムを大きく傷つけると水が入るので、細いものを使う。電線の被覆に穴を開ける方法は勧めない。

4測定の流れ

最初に配線が生きているかをライブ表示で確かめ、その後に状態ごとに1秒ずつ記録する。ライブ表示でエッジ数が増えていれば、信号が変化している。

① 書き込みは、Macで次を実行する。ctags の回避フォルダは、以前のハイビーム作業と同じ方法である。

cd ~/fit-gk-kaiseki/micro-control
mkdir -p /tmp/ctags && printf '#!/bin/sh\nexit 0\n' > /tmp/ctags/ctags && chmod +x /tmp/ctags/ctags
arduino-cli compile --upload -p /dev/cu.usbmodem5C630050101 \
  --fqbn esp32:esp32:esp32s3:CDCOnBoot=default \
  --build-property tools.ctags.path=/tmp/ctags firmware/led_sig_rec

③ 生存確認は、モニタを開いて m と Enter を送る。0.5秒ごとに次のような行が出る。

arduino-cli monitor -p /dev/cu.usbmodem5C630050101 --config baudrate=115200
m
# Y=0 (0 edges/0.5s)  X=0 (0 edges/0.5s)      ← ライトOFF
# Y=1 (812 edges/0.5s)  X=0 (0 edges/0.5s)    ← ロービームON。Yが動いている

ライトを入れてもYが0のまま、エッジも0なら、配線かバックプローブの当たりを見直す。Ctrl+C でモニタを閉じてから④へ進む。

④ 記録は、車の状態を変えるたびに1回ずつ実行する。ラベルは自由だが、次の5つをそろえると比べやすい。

順車の操作コマンド
1ライトスイッチOFF(イグニッションON)ledsig.py rec off
2車幅灯(ポジション)ledsig.py rec pos
3ロービームONledsig.py rec lo_on
4ハイビームONledsig.py rec hi_on
5パッシング(レバーを手前に引いたまま)ledsig.py rec hi_flash
cd ~/fit-gk-kaiseki
.venv/bin/python micro-control/tools/ledsig.py rec lo_on 1000

記録は micro-control/logs/ledsig/ に保存される。あとで5つまとめて見比べるときは、analyze にファイルを並べて渡す。

.venv/bin/python micro-control/tools/ledsig.py analyze micro-control/logs/ledsig/*.txt

5結果の読み方

判定は4種類で、どれになるかで次の再現のやり方が変わる。下の図は、それぞれの典型的な波形と表示である。

CONST ずっと同じレベル

Y: CONST  ずっと H(1000ms のあいだエッジなし)

ON/OFFを電圧の高低だけで伝えている。再現は、ESP32から一定のHighを出すだけで済む。ただし、12V・GNDだけで点かなかった事実と合わないので、可能性は低い(推測)。

PWM 一定の周期で点滅

Y: PWM    200.0Hz  周期4999µs  デューティ30.0%

周波数とデューティで明るさや点灯を伝えている。再現はESP32のPWMで同じ周波数とデューティを出せばよく、デューティを変えれば調光できる可能性が高い(推測)。

SERIAL 通信(バイト列)

Y: SERIAL 1ビット≒52µs → 約19231bps  標準値なら 19200bps(LIN)

車体コンピューターとユニットが会話している。再現にはバイトの中身の解読が要るので、ロジックアナライザでデコードする段階に進む。

IRREG どれにも当てはまらない

Y: IRREG  周期も整数倍もそろわない(下の分布を見る)
   H分布(µs×回): 52×52, 209×28, ...

判定が外れたか、ノイズが乗っている。下に出る分布と先頭16区間を見て判断する。ログファイルを渡してもらえれば、こちらで読む。

5状態を並べたとき、次のどこが変わるかを見る。ロービームONで初めて信号が出るのか、ポジションでも出ているのか、ハイビームで周期やデューティが変わるのか、である。ここが分かれば、ESP32から何を出せば点灯するかが決まる。

6次の段階(再現)の見取り図

記録の結果がPWMか一定レベルなら、ユニットを車から外し、12V・GND・ESP32の信号の3本で点灯させる。ESP32の出力は3.3Vなので、NPNトランジスタで5Vに持ち上げる。この回路はHighとLowが反転するため、ファーム側で反転して出す。

結果がSERIALだった場合は、この図のままでは点かない。バイトの中身をそのまま送り返す必要があるので、ロジックアナライザでのデコードを先に行う。

7注意

項目理由
抵抗は「上10k・下20k」の向き逆だと5Vが1.67VになりHighと判定されず、何も記録されない。
ESP32のGNDを車のGNDへつながないと信号が読めず、GPIOに想定外の電圧がかかる。
XとYを取り違えないYが本命で、Xは予備としてGPIO11で同時に記録する。逆につなぐと判定結果も入れ替わる。
エンジン始動中は記録しないセルモーターで電圧が大きく揺れ、ノイズが乗る。イグニッションONの状態で測る。
overflow と出たら ms を短く1回に記録できるエッジは16,384個まで。速い信号は500msなどに縮める。
